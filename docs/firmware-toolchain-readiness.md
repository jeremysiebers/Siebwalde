### 2.1 TrackAmplifier4.X — HEAD does not build (executed)

Exact first error (all three configurations, in `modbus/General.c` which includes
`modbus/PetitModbus.h`):

```
modbus/PetitModbus.h:61:60: error: (277) can't mix prototyped and non-prototyped arguments
modbus/PetitModbus.h:61:65: error: (372) "," expected
(908) exit status = 1
```

Cause: the refactor added `void OnHoldingRegisterWrite(uint16_t addr, uint16_t value, bool broadcast);`
(`PetitModbus.h:61`) but `PetitModbus.h` does not include `<stdbool.h>`; under the
project's C90 dialect `bool` is unknown, so the declaration is parsed as an old-style
(K&R) argument list. This is a **genuine compiler error**, not a missing toolchain.

After applying **diagnostic-only** temp patches (add `<stdbool.h>`, add a stub
`modbushooks.c`) to unmask the remaining errors, the following **genuine** HEAD defects
were observed (category in brackets):

- `[missing file]` `make[2]: *** No rule to make target 'modbus/modbushooks.c'` — the file
  is referenced by `nbproject/configurations.xml` but does not exist (never existed in
  any revision; `git log --all -- '*modbushooks*'` is empty).
- `[type mismatch]` `main.c:27: error: (984) type redeclared` /
  `(1098) conflicting declarations for variable "Update_AmplifierTicks"` — `main.c:27`
  declares `volatile uint32_t`, `main.h:18` declares `extern volatile uint8_t`, and
  `mcc_generated_files/interrupt_manager.c:107` increments via the `uint8_t`
  declaration.
- `[undefined symbol]` `main.c:160: undefined identifier "last_modbus_activity_tick"`.
- `[undefined symbol/type]` `main.c:162: undefined identifier "runtime_command"` and
  `struct/union required`.
- `[undefined symbols]` `CheckModbusTimeout()`, `Ramp_Update()`, `ControlCore_Update()`
  are called at `main.c:205-207` and are defined nowhere in the project.

**Classification:** this is an **incomplete project/source refactor**, not a missing
toolchain. The compiler itself is present and functional (it built the pre-refactor
baseline and the other projects).

### 2.2 Build-invocation gotcha (documented so future agents do not misattribute it)

Invoking `${MAKE}` for the sub-project step breaks when the project path contains
spaces and make is called through PowerShell `&` with an absolute path, because the
generated `.build-subprojects` recipe does not quote `${MAKE}`. Using `make` from
`PATH` under `cmd /c` works. This is a **build-invocation artifact**, not a project
defect.

**Conclusion (high confidence):** the committed artifacts predate the `b06f466`

**Residual uncertainty (must be reported, not resolved by invention):** there is no

image physically present in the amplifiers equals either committed HEX is **not

`PARTIALLY_PROVEN` at best.

### 4.2 Functionality actually implemented in the functioning baseline (`928ea7c`)

Reconstructed from `main.c`, `regulator.c`, `processio.c`, `modbus/` and
`mcc_generated_files/` (**inspected**):

- **Boot / identity / checksum:** `SYSTEM_Initialize()`; `ReadFlashChecksum()`
  (`main.c:463-470`) reads the 16-bit value at flash `0x008000-2` into
  `PetitHoldingRegisters[HR_SW_CHECKSUM]` (HoldingReg11). Config state machine
  (states 0/1/2/3/5): ID pin low (`ID_PORT`) → configuration mode; the master writes
  the ID into `HR_STATUS` bits 0-5 and the code latches `HR_STATUS_ID_SET_BIT`;
  `HR_SW_CHECKSUM == 0` triggers the bootloader invoke sequence ending in `RESET()`.
  Amplifier enable is gated on `HR_BEMF_CTRL & HR_BEMF_ENABLE_AMPLIFIER_BIT`
  (HoldingReg1 bit15) before `REGULATORxINIT()`.
- **HR0 → PWM control path (the requested reconstruction):**
  - `modbus/General.h:26-27`: `HR_PWM_COMMAND = 0` (HoldingReg0); bit layout at
    `General.h:63-69`: `HR_PWM_SETPOINT_MASK = 0x03FF` (bits 0-9), `HR_PWM_DIR_BIT`
    (bit 10), `HR_PWM_BRAKE_BIT` (bit 11), `HR_PWM_EMO_BIT` (bit 15).
  - `REGULATORxINIT()` (`regulator.c:25-43`): neutral `PwmDutyCyclePrev = 399`,
    `PWM3_LoadDutyValue(399)`, outputs TRISC4/5/6, `PWM3EN = true`, `LM_PWM_LAT = true`,
    and sets the setpoint bits of `HR_PWM_COMMAND` to 399.
  - `REGULATORxUPDATE()` (`regulator.c:61-89`): reads `cmd = HR_PWM_COMMAND`; if
    `cmd & HR_PWM_EMO_BIT` → `LM_BRAKE_LAT = true` and return (no duty write);
    otherwise `LM_BRAKE_LAT = false`, `duty = cmd & HR_PWM_SETPOINT_MASK`, clamps
    `duty == 0` to `1` (comment: remote TMR2 reset makes 0 unreachable), and
    `PWM3_LoadDutyValue(duty)` only on change.
  - `PWM3_LoadDutyValue` splits into `PWM3DCH/PWM3DCL`
    (`mcc_generated_files/pwm3.c:74-81`); `PWM3_Initialize` selects TMR2.
  - **Not consumed in the baseline:** `HR_PWM_DIR_BIT` (bit 10) and
    `HR_PWM_BRAKE_BIT` (bit 11) are defined but never used; `LM_DIR_LAT` (LATC6) is
    only cleared once (`main.c:55`). Brake is driven solely by the EMO bit.
- **BEMF measurement:** `MEASURExBMF()` (`processio.c:32-96`) tristates the H-bridge,
  uses TMR1 (`0xFF38`) to measure back-EMF late in the off-window; `ADC_BMF()`
  (`processio.c:119-143`) stores the result into the static `g_bemf` (the header
  comment claiming it writes `HR_STATUS` directly is inaccurate; `ADCxIO` composes it).
- **Analog measurement routing:** `ADCxIO()` (`processio.c:172-269`) multiplexes
  `LM_V → HR_FUSE_VOLTAGE` (HoldingReg4), `LM_TEMP → HR_HBRIDGE_TEMPERATURE`
  (HoldingReg5), `LM_CURR → HR_HBRIDGE_CURRENT` (HoldingReg6), and composes
  `HR_STATUS` bits: occupancy from `CMP1_GetOutputStatus()` (bit 10), thermal from
  `LM_THFLG_GetValue()` (bit 11), BEMF in bits 0-9. `HR_STATUS_OVERCURRENT_BIT`
  (bit 12) is never set.
- **Modbus:** `PetitModbus` with 12 holding registers only
  (`NUMBER_OF_INPUT_PETITREGISTERS = 0`, diagnostics = 0; FC03/06/16 enabled), 9th-bit
  hardware addressing (`interrupt_manager.c:77-78,97`), message counters in
  `HR_MESSAGES_RECEIVED`/`HR_MESSAGES_SENT`.
- **Tick:** `interrupt_manager.c:102-108` increments the tick on TMR4 overflow.

This matches the product-owner observation that the running firmware accepts PWM
setpoints, has an emergency-stop path (the HR0 EMO bit), and returns measurements
(HR4/5/6 and HR_STATUS).

### 4.3 The incomplete refactor (`b06f466`) — target vs reality

`b06f466` replaced the working `MEASURExBMF → REGULATORxUPDATE → ADCxIO` sequencer with
`if (AmplifierTick_Elapsed()) AmplifierPeriodicTasks();` plus a bare Modbus-timeout
check, and added the `OnHoldingRegisterWrite` hook. The old sequencer was left as dead
comment code (`main.c:165-197`). The intended target architecture, described by the
docs added in the same commit, is a **central Control Core**:

- `TRACK_AMPLIFIER_STATE_MACHINE.md` (678 lines) — runtime states
  (`NOT_INITIALIZED/READY/RUN/STOPPING/EMERGENCY_STOP/FAULT/COMMS_LOST`), transition
  table, fixed priority (`FAULT > EMERGENCY_STOP > COMMS_LOST > NOT_INITIALIZED >
  STOPPING > RUN > READY`), `ControlCore_EvaluateState`, stop via `PWM_STOP_DUTY = 399`,
  comms-watchdog kick sources, init gating and invariants.
- `AGENT_TRACK_AMPLIFIER.md` (419 lines) — `control_core.c` module, the
  `OnHoldingRegisterWrite` callback, two-phase pending/active config with `APPLY`,
  ramp (`current_pwm → target_pwm`), comms watchdog, command priority, and §20 requiring
  the `volatile uint32_t Update_AmplifierTicks` + `bool AmplifierTick_Elapsed(void)`.
- `AGENT_TRACK_AMPLIFIER_COMPACT.md` (262 lines) — condensed restatement.
- `MODBUS_TRACK_AMPLIFIER_MAPPING.md` (513 lines) — read-only telemetry to Input
  Registers `InputReg0..7` + Diagnostic Registers, `APPLY_PENDING_CONFIG`
  (HoldingReg1 bit13), HoldingReg9/10 config/ramp words, plus a transitional
  compatibility layer.

**Implementation status:** none of the Control Core, ramp, watchdog, two-phase config or
register remap is implemented. `General.h` shows the register constants, but the Input/
Diagnostic register counts remain 0 and no `control_core`/`modbushooks` files exist.
The only part of the refactor that partially landed is the tick helper (§20), and even
that does not compile.

### 4.4 What "coherent, reproducibly buildable baseline" requires

The `928ea7c` source tree compiles and links cleanly with the locally installed XC8
v2.31 (executed, §2). The `b06f466` HEAD tree does not compile in any configuration.
Because `b06f466` is an **incomplete safety-architecture rewrite** (central PWM
ownership, state machine, watchdog, ramp, two-phase config) rather than a build fix,
the recommended route is to treat `928ea7c` as the reference buildable baseline and
complete the refactor as a separate, safety-classified increment. Completing the
refactor with dummy/stub implementations of control or safety functions merely to
satisfy the compiler is **explicitly rejected**: it would produce a binary that appears
to build while the state machine, ramp, watchdog and APPLY gating are non-functional —
a false safety guarantee.

This is a **material product/safety decision** (see §11) and is not taken here.

## 5. Deliverable 5 — Proposal: automated firmware builds and software tests

### 5.1 Automated build harness (proposed)

A repository build harness (for example `tools/firmware/build-firmware.ps1`) should:

1. Pin toolchains by absolute path: MPLAB X **v6.05** for `TrackAmplifierBootLoader.X`
   (DFP 1.7.134) and **v6.20** for `TrackAmplifier4.X`, `TrackBackplane2.X` and
   `TrackController5`; XC8 v2.31 for PIC18 application/backplane, XC8 v2.40 for the
   bootloader `No_Configurations`, XC32 v2.50 for PIC32.
2. Regenerate `nbproject/Makefile-*.mk` with `prjMakefilesGenerator.bat` into a
   **clean out-of-tree build directory** (never in the tracked tree), so tracked
   `dist/*.hex` is never overwritten.
3. Build each configuration, capture the full log, and fail on any error.
4. Emit/report the artifact SHA-256 and, where present, the in-flash checksum.
5. Be safe/read-only by default: never flash, program or enumerate hardware.

Decision needed: commit the generated `Makefile-*.mk` files for byte-stable
reproducibility, or require per-machine regeneration (see §11).

### 5.2 Software tests — what is realistically testable (with explicit boundaries)

There is **no host test framework for the PIC C code today**, and the code is tightly
coupled to XC8/`xc.h` and MCC register access, so a native host compile of production
modules is not currently possible without introducing a hardware-abstraction layer.
Proposed staged approach:

- **V1 (now, no firmware change): compile-under-XC8 as the strongest automated check.**
  The build harness above proves compilation/linking per configuration. This is real
  (E2) evidence and already distinguishes "missing toolchain" from "source defect".
- **V2 (host protocol regression, no firmware change):** extend the C# deterministic
  protocol tests (see §7). These exercise the **host↔master protocol frames**, not the
  PIC firmware logic.
- **V2/V3 (later, requires firmware work):** introduce a thin hardware-access
  abstraction (or compile-time host shim) for the pure logic of `REGULATORxUPDATE` /
  ramp / state machine, so those functions can be compiled and unit-tested on the host.
  This is a design change and must be its own increment.
- **V2 (later):** evaluate the MPLAB X simulator / `mdb` for on-simulator firmware unit
  tests. `mdb` is not currently on `PATH`; feasibility is unverified.

**Mandatory evidence boundary:** a C# protocol simulator or a host-side C harness is
**not** a unit test of the actual PIC firmware. Software-only evidence must never be
used to overclaim physical PWM/timing/safety behaviour (Workflow v1 §8.2/§9.1).

## 6. Deliverable 6 — Proposal: artifact identification, checksums and traceability

Existing mechanisms (**inspected**):
- The PIC18 application stores a 16-bit flash checksum at `0x7FFE/0x7FFF` and exposes
  it as `HR_SW_CHECKSUM` (HoldingReg11).
- The host (`TrackAmplifierBootloaderHelpers.Execute`) reads the Offset HEX, computes a
  16-bit checksum over the first `(0x8000 − 0x800)/16 = 1920` rows, and compares it with
  each detected amplifier's HoldingReg11 to decide whether flashing is needed.
- A cross-check executed during this increment: the host checksum algorithm applied to
  `TrackAmplifier4.X/dist/Offset/production/TrackAmplifier4.X.production.hex` yields
  **`0x251F`**, equal to `TrackSimulatorConfig.DefaultFirmwareChecksum` — the simulator's
  "no flashing needed" path is calibrated to the shipped HEX.

Proposed additions:
1. **Artifact manifest** next to each produced firmware image: source revision (full Git
   SHA + dirty flag), configuration name, compiler/toolchain versions, device, artifact
   SHA-256, in-flash checksum, and build date.
2. **Build ID in the target:** embed the short Git SHA (and dirty flag) into a reserved
   register (or reserved flash word) so the running firmware can report exactly which
   source it came from. This needs product/register-map approval.
3. **Never overwrite existing artifacts.** New builds go to a versioned/out-of-tree
   output location; tracked historical HEX files stay immutable as evidence anchors.
4. **Record checksum provenance**: document the exact host checksum algorithm
   (row range, byte order, skipped bytes) so a mismatch is diagnosable rather than
   mysterious.

  encode/parse path is exercised by `DeterministicTrackTransportEndToEndTests` and

Proposed integration:
1. Treat the parallel **Full Software Simulation** increment and

## 8. Deliverable 8 — Proposal: controlled firmware flashing and physical validation

The existing end-to-end update path (**inspected**):
Intel HEX (`dist/Offset/...`) → host reads it and computes a checksum
(`TrackAmplifierBootloaderHelpers`) → compares with each amplifier's `HR_SW_CHECKSUM` →
if different: `EXEC_MBUS_STATE_SLAVE_FW_FLASH (103)` and FSM states 1-9
(`SendNextFwDataPacket`, 4 rows × 16 B = 64 B/packet) → PIC32 `slavefwhandler.c` buffers
into `FwFile`, recomputes/compares the checksum → backplane slot select + write `0` to
`SLAVE_INITIAL_ADDR (0xAA)` HR11 → PIC18 `main.c` sees `HR_SW_CHECKSUM == 0` and calls
`RESET()` → MCC bootloader (`0x55` STX; erase/write/config/checksum/reset) → app
restarts at `0x800`, UART2 returns to 9-bit Modbus.

Proposed controlled workflow under Workflow v1 (all currently **not authorized**):
1. **Prepare (autonomous, safe):** produce the artifact out-of-tree, verify checksums,
   record the manifest, prepare the exact command and stop/cleanup procedure.
2. **Authority gate:** `FIRMWARE_FLASH` **and** `LIVE_HARDWARE`, scoped to increment,
   revision, artifact hash, target hardware and session. These are non-transitive and
   revision-bound (Workflow v1 §9.4/§11).
3. **Visible session:** a visible operator session (prefer a `SIEBWALDE LIVE TEST`
   window) with a documented PID, exact command, working directory, manual stop and
   automatic timeout.
4. **Stop/cleanup:** command neutral, verify neutral at the nearest observable layer,
   stop the runtime, verify termination; process exit is **not** proof of hardware
   neutralization.
5. **Evidence:** record pre/post checksums and physical observations as E4 evidence with
   provenance; an unknown physical state becomes `UNKNOWN_EXECUTION_STATE`, not success.
