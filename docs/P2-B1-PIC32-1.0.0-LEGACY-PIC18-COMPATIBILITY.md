# P2-B1 Compatibility Analysis — PIC32 master 1.0.0 (protocol 1) vs DEPLOYED legacy PIC18 amplifiers (12-register, HR11=0x251F)

- **Role:** Architect (read-only source analysis)
- **Date:** 2026-10-25
- **Worktree:** `C:\Localdata\Siebwalde`, master `c9938c83`
- **Target firmware source analyzed:** `TrackController5` (PIC32 master), protocol 1 at `CTRL_FW 1.0.0` (`firmware/src/version.h:6-9`, `CTRL_PROTOCOL_VERSION 0x01`)
- **Scope:** PIC32 master `1.0.0` (protocol 1) communicating with deployed PIC18 amplifiers that still run the LEGACY 12-register firmware. PIC18 firmware is NOT changed in this increment.

## Verdict

**`COMPATIBLE_WITH_RISKS`**

The 1.0.0 master can be powered against legacy 12-register PIC18 slaves without bricking them, causing Modbus exceptions, or autonomously flashing them. The master's Phase-1 identity gate correctly classifies legacy slaves as **incompatible** and leaves them untouched (not re-addressed, not enabled, not written to). The only material risk is the **host-commanded bulk flash path**, which is checksum-selective with **no identity/protocol gate**: if the C# host runs `FlashFwTrackamplifiersStep` (or any `EXEC_FW_STATE_*` flash command) during the test, the master **will** flash the legacy PIC18 slaves. This must be explicitly excluded.

## 1. FC03 read length — what the 1.0.0 master actually reads per slave

**The master NEVER reads 23 registers (or even 12) in a single FC03.** Every holding-register read is capped at **2 registers** by the transport handler:

- `SLAVExCOMMUNICATIONxHANDLER()` READ branch sets `ReadData[3] = 1` (one register) and only increments to `2` if `Data.NoOfRegisters > 1` — `TrackController5/firmware/src/slavecommhandler.c:107-118`. There is no path that issues a >2-register FC03.

The cyclic poll (`SendNextMessage()`, `TrackController5/firmware/src/slavehandler.c:264-419`) reads the 23-register map in 2-register chunks (last chunk 1 register):

| Phase | Start register | Length | Source |
|---|---|---|---|
| MESSAGE1 | HR0 (`HOLDINGREG0`) | 2 | slavehandler.c:336-342 |
| MESSAGE2 | HR2 | 2 | slavehandler.c:344-350 |
| MESSAGE3 / SIP1 | HR4 | 2 | slavehandler.c:355-361 |
| MESSAGE3 / SIP2 | HR6 | 2 | slavehandler.c:363-369 |
| MESSAGE3 / SIP3 | HR8 | 2 | slavehandler.c:371-377 |
| MESSAGE3 / SIP4 | HR10 | 2 | slavehandler.c:379-385 |
| MESSAGE3 / SIP5..SIP9 | HR12 + 2·(n−5) (→ HR12,14,16,18,20) | 2 | slavehandler.c:387-393 |
| MESSAGE3 / SIP10 | HR22 | 1 | slavehandler.c:390-392 |

Register-number constants: `HR_IDENTITY=7`, `HR_STATE=8`, `HR_REQUESTED_PWM=12`, `HR_APPLIED_PWM=14`, `HR_FW_VERSION=21`, `HR_FW_VERSION_PATCH_PROTO=22` — `TrackController5/firmware/src/enums.h:97-109`.

**Startup reads to the pre-address bus address (`SLAVE_INITIAL_ADDR = 0xAA`, enums.h:327) are both single-register and in-range for a 12-register slave:**
- Detect: read HR11 (checksum), 1 register — `slavestartup.c:293-297` (`Data.NoOfRegisters = 1`, `Data.StartRegister = HOLDINGREG11`).
- Identity verify: read HR7, 1 register (twice) — `slavestartup.c:29-37` (`Data.NoOfRegisters = 1`, `Data.StartRegister = HR_IDENTITY`).

**Conclusion:** the maximum single FC03 read is 2 registers; the only reads sent to `0xAA` (where legacy slaves live) are HR7 and HR11, both inside the 12-register range. No 23-register read, no out-of-range single read.

## 2. Does a 12-register slave cause an exception/fault, or a graceful degraded read?

**Graceful degradation — no Modbus exception reaches a legacy slave.**

The out-of-range reads (HR12..HR22, i.e. SIP5..SIP10) are only ever addressed to the *assigned* slave IDs 1..50 (`Data.SlaveAddress = ProcessSlave`, slavehandler.c:337/345/356/…). A legacy slave is **never assigned** an ID because the identity gate fails first (see §3), so it keeps `0xAA` (`SLAVE_INITIAL_ADDR`). Therefore:

- The HR12+ polling is sent to addresses 1..50, which no legacy slave occupies → the master records `SLAVE_DATA_TIMEOUT` for those slots, not an exception. (`MbCommError` is a `SLAVE_DATA` enum including `SLAVE_DATA_TIMEOUT`, PetitModbus.h:56-65.)
- The only reads that physically reach a legacy slave are HR7 and HR11 at `0xAA`, both in-range → the legacy slave answers normally; the master then *rejects it on identity shape*, not on a Modbus error.

## 3. HR7 identity check — master or host only?

**It lives in the PIC32 master (primary), and is mirrored in the C# host.**

Master-side, `VERIFYxAMPLIFIERxIDENTITY()` (`slavestartup.c:23-59`) reads HR7 twice from `0xAA` and sets `AmplifierCompatible[slave]` only if:

```c
status == SLAVEOK && phase == 3 &&
identity == first &&                 // two consecutive reads identical
(identity & 0xffu) == 1u &&          // low byte == 1
(identity & 0x0f00u) == 0x0100u &&   // protocol nibble == 1
(identity & 0xf000u) != 0;           // family nibble non-zero
```
`slavestartup.c:47-49`.

A legacy HR7 of `0x002D` / `0x002E` fails **all three** shape terms (`0x2D & 0xff ≠ 1`, `0x002D & 0x0f00 == 0 ≠ 0x0100`, `0x002D & 0xf000 == 0`). `AmplifierCompatible` is `false`.

Consequences of `!ISxAMPLIFIERxCOMPATIBLE(slave)` (gate defined at `slavestartup.c:16-19`):
- **No address assignment** — `ConfigureSlave` case 10 routes incompatible slaves to case 5 (deselect slot) instead of case 3 (write `HOLDINGREG2 = TrackAmplifierId`) — `slavestartup.c:535-539`, `541-555`.
- **No enable** — `ENABLExAMPLIFIER` skips incompatible slaves — `slavestartup.c:659-660`.
- **No host writes** — `ADDxNEWxSLAVExDATAxCMDxTOxSLAVExMAILBOX` drops WRITE commands to incompatible amplifier IDs — `slavehandler.c:506-508`; the transport-level guard also drops them — `slavecommhandler.c:78-83`.
- **No global-stop delivery** — `ENQUEUExGLOBALxSTOP` marks incompatible slaves `STOP_FAILED` — `slavehandler.c:562-568`.

The C# host also checks HR7/HR_STATE independently from the SLAVEINFO stream (noted in `TrackController5/firmware/src/tests/README-phase1.md:27`), but that check is **not** part of the flash path (see §7).

## 4. HR21/HR22 (version) read

HR21 (`HR_FW_VERSION`) and HR22 (`HR_FW_VERSION_PATCH_PROTO`) are **defined** (`enums.h:108-109`) and are polled as part of the register map (SIP9 reads HR20–HR21, SIP10 reads HR22 — `slavehandler.c:387-393`), but they are **never interpreted by the master**. A repository-wide grep shows no other reference to `HR_FW_VERSION*` anywhere in `TrackController5/firmware/src` outside the `enums.h` definitions.

- No version-driven decision, no HR21/HR22 comparison, no fault on their content.
- Because those reads only go to assigned addresses (1..50), a legacy slave (at `0xAA`) never receives them, so there is also no exception from a legacy slave on HR21/HR22.

## 5. ENABLE / motion-permission semantics

The 1.0.0 enable path **requires** a Phase-1 identity before enabling a slave:

- `ENABLExAMPLIFIER()` writes `0x8000` to HR1 only for slaves where `ISxAMPLIFIERxCOMPATIBLE(slave)` is true — `slavestartup.c:657-671`. Legacy slaves are skipped → they never receive the enable word.
- The periodic motion lease is a **broadcast** write (`Data.SlaveAddress = BROADCAST_ADDRESS`, HR1 = `MOTION_PERMISSION_HR1 = 0x4000`) every 100 ms — `slavehandler.c:274-283`. This is a *write* to HR1 (in-range for a 12-register slave), not a read; a legacy slave would accept it without exception. `0x4000` is a distinct bit from the `0x8000` enable word (`enums.h:93`), so it does not by itself enable legacy motion, but the bit's meaning on legacy firmware is **not verified** — noted as a residual, low-severity risk below.

## 6. Checksum (HR11 = 0x251F) interpretation

The master **does not** interpret HR11 to make any decision during normal startup/init/service. It only *stores* the detected checksum:

- `DetectSlave` reads HR11 and stores it: `MASTER_SLAVE_DATA[SlaveId].HoldingReg[HOLDINGREG11] = DUMP_SLAVE_DATA[0].HoldingReg[HOLDINGREG11]` — `slavestartup.c:306-308`.

There is **no** autonomous "checksum mismatch → flash" logic in `SLAVExDETECT`, `SLAVExINITxANDxCONFIG`, `ENABLExAMPLIFIER`, or the SERVICE_TASKS polling loop. The only checksum-selective flash logic is inside the **host-commanded** flash handler (see §7).

## 7. Auto-flash exclusion (critical)

**The PIC32 master has no autonomous auto-flash path.** Every flash/bootloader operation is driven by an explicit host command, dispatched through `SLAVExFWxHANDLER()`:

- `MBUS_STATE_SLAVE_FW_FLASH` is entered **only** via `SETxMBUSxSTATE(MBUS_STATE_SLAVE_FW_FLASH)`, which is triggered **only** by the host command `EXEC_MBUS_STATE_SLAVE_FW_FLASH` — `controller.c:340-345`.
- `SLAVExFWxHANDLER()` consumes flash commands (`EXEC_FW_STATE_FLASH_ALL_SLAVES`=122, `EXEC_FW_STATE_ERASE_FLASH`=125, `EXEC_FW_STATE_WRITE_FLASH`=126, `EXEC_FW_STATE_SELECT_SLAVE`=123, `EXEC_FW_STATE_WRITE_CONFIG`=127, `EXEC_FW_STATE_CHECK_CHECKSUM`=128, `EXEC_FW_STATE_SLAVE_RESET`=129, …) from the **receive mailbox** (i.e., the host) — `slavefwhandler.c:143-478`.
- `FlashAllSlavesAuto()` is the checksum-selective bulk flash: for each detected slave, `if ((SlaveDetected == true) && (HoldingReg[11] != fwData.fwchecksum))` → flash that slave — `slavefwhandler.c:744-759`. The bootloader entry is `write HOLDINGREG11 = 0` to the selected slave (`FlashSequencer` case 6 — `slavefwhandler.c:932-945`).

**Critical: this checksum-selective logic has NO identity/protocol gate.** A legacy PIC18 (HR11 = `0x251F`) will differ from any downloaded Phase-1 file checksum, so `FlashAllSlavesAuto` **will flash it** if the host sends `EXEC_FW_STATE_FLASH_ALL_SLAVES`.

The C# host mirrors the same ungated checksum logic in `FlashFwTrackamplifiersStep.State0_DetermineFlashRequirementAsync` — a slave is selected for flashing when `checksum != HoldingReg[SwChecksum] && SlaveDetected == 1 && 0 < SlaveNumber < 51` (`FlashFwTrackamplifiersStep.cs:139-153`), then the host sends `EXEC_MBUS_STATE_SLAVE_FW_FLASH` → … → `EXEC_FW_STATE_FLASH_ALL_SLAVES` (`FlashFwTrackamplifiersStep.cs:170-180`, `424-436`). **No identity gate there either.**

`RecoverSlavesStep` is a *single-slave* path that first probes `EXEC_FW_STATE_GET_BOOTLOADER_VERSION` and only proceeds if a slave is **already in bootloader mode** (`GET_BOOTLOADER_VERSION_OK`); a normally-running legacy PIC18 does not answer the bootloader probe, so `RecoverSlavesStep` stops with error rather than flashing (`RecoverSlavesStep.cs:184-226`). It is therefore lower-risk than `FlashFwTrackamplifiersStep`, but should still be excluded from the test.

### Exclusion requirement (test-time)

Because the master is a **willing executor** of host-commanded bulk flash, the P2-B1 test MUST guarantee:

1. The C# host does **not** run `FlashFwTrackamplifiersStep` (and does not emit `EXEC_MBUS_STATE_SLAVE_FW_FLASH` / `EXEC_FW_STATE_FLASH_ALL_SLAVES` / any `EXEC_FW_STATE_*` flash command).
2. `RecoverSlavesStep` is also not run (or is confirmed to terminate on `GET_BOOTLOADER_VERSION_NOK` without any erase/write).
3. No Phase-1 firmware file is made available to the bootloader helpers while the legacy slaves are on the bus.

If these hold, the master will not flash legacy slaves.

## 8. SLAVEINFO upload size (wire layout change)

`UPLOAD_STATE_ALL` copies `sizeof(SLAVE_INFO)` into the upload frame — `mbus.c:415-433` (`memcpy(&data.data, &(SlaveInfo[NextSlaveCounter].Header), sizeof(SLAVE_INFO))`).

`SLAVE_INFO` (PetitModbus.h:67-80) is register-count-derived (`HoldingReg[NUMBER_OF_HOLDING_PETITREGISTERS]`, PetitModbus.h:72), so with `NUMBER_OF_HOLDING_PETITREGISTERS = 23` (PetitModbus.h:15) the struct is **64 bytes** (footer at struct offset 60 / wire offset 62, padded to 4-byte alignment), versus the legacy 12-register **40-byte** struct (footer at wire offset 40). This is a wire-layout change only.

The C# decoder is **layout-aware** and handles both:
- `TrackSlaveInfoFrame.cs` encodes the 23-register Phase-1 layout and documents the legacy 12-register layout constants (`TrackSlaveInfoFrame.cs:9-35`); `TrackAmplifierRegisters.Count = 23`, `SwChecksum = 11`, `Identity = 7` (`TrackAmplifierRegisters.cs:6,9`).
- `tools/diagnostics/slaveinfo_decoder.py` decodes the 23-register map and explicitly notes the legacy 12-register distinction (`slaveinfo_decoder.py:264-271`).

Host-side decode is therefore fine; no PIC32-side change is needed for upload.

## Risks / mitigations

1. **Host-commanded bulk flash would flash legacy slaves (HIGH).** Mitigation: exclude `FlashFwTrackamplifiersStep` and `RecoverSlavesStep`, and all `EXEC_FW_STATE_*` flash commands, from the P2-B1 test; do not supply a Phase-1 firmware file to the bootloader helpers. This is the gating condition for the `COMPATIBLE_WITH_RISKS` verdict.
2. **Motion lease broadcast `0x4000` to HR1 reaches legacy slaves (LOW, unverified).** `0x4000` is a distinct bit from the `0x8000` enable word and should not enable legacy motion, but the legacy firmware's interpretation of HR1 bit 0x4000 is not verified in this analysis. Recommend confirming against the legacy PIC18 `General.h`/`modbushooks` mapping before deeming motion-safety proven.
3. **Legacy slaves are functionally inert under the 1.0.0 master (EXPECTED).** Because the identity gate fails, legacy slaves will appear as "detected but incompatible" (init ERROR per slave — `slavestartup.c:54-56`) and will not be enabled, addressed, or successfully polled. This is the intended outcome given PIC18 firmware is unchanged, but the test assertions should expect this, not motion.

## Unverified / assumptions

- Legacy HR7 raw values `0x002D`/`0x002E` are taken from the task context (K8B read); not independently re-read from hardware here.
- Legacy HR1 bit semantics for `0x4000` are not verified against the legacy PIC18 source in this analysis.
- The exact backplane slot-select electrical model during SERVICE_TASKS was not re-derived; the conclusion that legacy slaves are not reachable by HR12+ reads holds regardless, because those reads target assigned IDs 1..50 that legacy slaves never receive.
